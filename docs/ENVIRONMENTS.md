# Окружения и цели прогонов

Все прогоны трогают **только стенд** — и чтение, и запись. Все цели — публичные
имена хостов; прод (`tamir.rs`, `www.tamir.rs`, `api.tamir.rs`) запрещён на уровне
кода: `qa/config.py::is_allowed_target` поднимает `RuntimeError` при попытке туда
пойти, `qa/http.py::QaHttpClient` проверяет хост перед каждым запросом. Правило
одинаковое и для read-only проверок, и для сценариев, которые создают корзины и
заказы: мутация не является оправданием для запроса на прод.

## Адреса стенда

| Что | Адрес |
| --- | --- |
| витрина (основная локаль) | `https://test.tamir.rs` |
| сербская копия витрины | `https://test.tamir.rs/rs` |
| Medusa API (store и admin) | `https://test-api.tamir.rs` |
| отчёты прогонов (Allure) | `https://qa.tamir.rs/<номер прогона>/` |
| тест-менеджер (Kiwi TCMS) | `https://tcms.tamir.rs` |
| почта стенда (Mailpit) | `http://192.168.1.143:8025` — только из локальной сети |

Витрина и API стоят за Cloudflare; сами сервисы — на staging-хосте в локальной сети
(`192.168.1.143`). Отсюда ограничение по исполнению: **прогоны со сценариями идут на
self-hosted runner** (`tamir-qa`), потому что Mailpit наружу не отдаётся, а очередь
из прогонов на одном runner'е ещё и разборчивее: параллельные прогоны путаются в
заказах и остатках на складе. GitHub-hosted джобы (`qa-unit`, `qa-report`)
используются только для офлайн-проверок и сборки отчёта, где запросов на стенд нет.

Белый список `qa/config.py::ALLOWED_HOSTS`:

| Цель | Адрес | Как используется |
| --- | --- | --- |
| Витрина (web storefront) | `https://test.tamir.rs` | read-only smoke (`robots.txt`, `sitemap.xml`, `/rs`, редирект `/`), контроль индексации (§13 TEST-PLAN), каталог, карточка товара, корзина и оформление (SSR), браузерные пути покупателя (§14) |
| Medusa API | `https://test-api.tamir.rs` | store- и admin-API: сценарии оформления заказа (§15), отмена заказа и уборка (§16), сверка заказа браузерного прогона |
| UI отчётов QA (self-hosted Allure + индекс прогонов) | `https://qa.tamir.rs` | публикация результатов джобом `qa-publish` |
| Kiwi TCMS (тест-планы и тест-кейсы) | `https://tcms.tamir.rs` | учёт тестов; интеграция через JSON-RPC `/json-rpc/` — см. [TCMS.md](TCMS.md) |
| Mailpit (перехватчик почты) | `192.168.1.143:8025` (LAN staging) | чтение писем и кодов в браузерных и API-сценариях; доступен только с self-hosted runner на staging |

## Маркеры и куда они ходят

| Маркер | Откуда | Куда ходят | Что проверяют |
| --- | --- | --- | --- |
| `unit` | `tests/unit/` | никуда, офлайн | guard по хостам, парсеры `qa/seo.py`, HTTP-клиент, индекс прогонов, клиент TCMS |
| `smoke` | `tests/smoke/` | витрина | доступность витрины: `robots.txt`, `sitemap.xml`, `/rs`, редирект корня |
| `api` | `tests/api/` | Medusa API | поведение `x-publishable-api-key`, состав полей заказа, сценарий оформления заказа через API |
| `seo` | `tests/seo/` | витрина | один контроль: non-prod закрыт от индексации (`X-Robots-Tag: noindex` или запрет в `robots.txt`) — см. [TEST-PLAN.md](TEST-PLAN.md), §13.1 |
| `catalog` | `tests/catalog/` | витрина | витрина каталога отвечает и содержит заголовок; список, счётчик, цена, поиск, карточка товара, SSR корзины и оформления, локализация `sr`/`en` |
| `e2e` | `tests/e2e/` | витрина + Medusa admin | браузерные пути покупателя (гость, шлюз регистрации, стендовый аккаунт) и отмена заказа админкой |
| `scenario` | `tests/e2e/`, `tests/api/` | витрина / Medusa API | сквозные пользовательские сценарии: оформление, отказ по остаткам, письмо покупателю |
| `checkout` | `tests/e2e/`, `tests/api/` | витрина / Medusa API | оформление заказа: двухшаговая отправка формы (браузер) и `POST /store/carts/{id}/complete` (API) |
| `tcms` | `tests/api/` | Kiwi TCMS | читающие проверки TCMS, запускаются вручную |

Ручной прогон того же набора, что в CI:

```bash
pytest -m "(unit or smoke or api or seo or catalog) and not (scenario or e2e)"  # job qa-smoke
pytest -m "e2e or scenario"                          # job qa-e2e
```

## Что знает конфигурация про индексацию

`QaConfig.site_origin` берёт публичный origin из таблицы `STAGING_SITE_ORIGINS`
(`test.tamir.rs` → `https://tamir.rs`), потому что продуктовый
`frontend/src/lib/seo.ts` считает публичным только прод-домен: на стенде
`canonical` и alternates всегда ведут на `tamir.rs`, хотя запросы идут на
`test.tamir.rs`. Смысл у таблицы один — отличить **чужой** домен в `robots.txt`
от стендового, не делая запрос на прод. Сам публичный домен остаётся запрещённым:
в `ALLOWED_HOSTS` есть `qa.tamir.rs` и `tcms.tamir.rs` (сервисы QA-стека на
staging), а `tamir.rs`, `www.tamir.rs`, `api.tamir.rs` — нет. Контракт
`canonical`/`hreflang` из плана снят (см. [TEST-PLAN.md](TEST-PLAN.md), §13):
`qa/seo.py` разбирает только `robots.txt` и `noindex`.

`QaConfig.expects_noindex` говорит, должно ли окружение быть закрыто от поисковых
систем: `False` бывает только если `QA_IS_PRODUCTION` выставлен в `1`/`true`/`yes`,
и тогда проверка `test_staging_zakryt_ot_indeksacii` снимается как неприменимая.

## Тестовые данные на стенде

Сценарии M2 и M3 пишут данные на стенде: корзины, заказы и тестовые покупатели.
Каждая такая сущность помечается (`metadata.qa_run` с меткой прогона — метка
переходит из корзины в заказ; почта вида `qa-…@example.com`), а после прогона
убирается (`scripts/qa_cleanup.py` в job `qa-e2e`, шаг с `if: always()`). Заказ на
стенде **не удаляется** — отменяется через `POST /admin/orders/{id}/cancel`, поэтому
отменённые QA-заказы в списке админки остаются; это ожидаемое состояние стенда, а не
ошибка. Подробности и список разрешённых мутаций — [TEST-PLAN.md](TEST-PLAN.md), §16.

## Особенности стенда

Проверенные на живом стенде вещи, о которых нужно помнить, когда тест «не сходится»
с реальностью (подробнее — [FINDINGS-frontend-backend.md](FINDINGS-frontend-backend.md)):

| Особенность | Что с этим делают тесты |
| --- | --- |
| корзина через store API читается только READ-эндпоинтами: `GET /admin/carts` и `DELETE /store/carts/{id}` отвечают 404 | позиции снимают `DELETE /store/carts/{id}/line-items/{line_id}` — иначе позиция держит резерв на складе стэнда |
| `customer_id` у заказа через store API не читается: `fields=customer_id` даёт `[]` | связь «покупатель ↔ заказ» устанавливают по e-mail покупателя |
| `quantity_available` витрина не отдаёт (всегда `0`) | остаток берут из `GET /admin/variants/{id}/inventory`, а «товар кончился» проверяют как ответ сервера на превышение количества |
| форма логина использует `input[name="email password"]` | селектор собран в `qa/ui.py`, менять URL при проверке нельзя — маршруты англоязычные, а адрес в строке может остаться «старым» |
| счётчики «0/8» в корзине — это максимум по позиции, а не количество | тесты читают пару «количество / доступный максимум», а не одно число |
| `POST /store/carts/{id}/complete` возвращает `metadata: null` | заказ дочитывается по `display_id`, и уже там виден `metadata.qa_run` |
| на стэнде лимит «не более 5 входов в час» | браузерные тесты входят один раз за прогон, стендовый аккаунт E2E-3 не удаляется |

## Переменные и секреты

Значений в репозитории нет — он публичный. Всё приходит только из переменных
окружения: в CI это GitHub Actions secrets, локально — `.env` (файл в `.gitignore`).
Без нужных переменных зависящие от них проверки скипаются, а не падают.

| Переменная | Зачем | Без неё |
| --- | --- | --- |
| `QA_WEB_EMAIL`, `QA_WEB_PASSWORD` | стендовый покупатель для браузерного пути E2E-3 | `test_registered_customer_journey.py` скипается |
| `MAILPIT_URL` | адрес Mailpit (`http://192.168.1.143:8025`) | проверки почты скипаются |
| `MAILPIT_USER`, `MAILPIT_PASSWORD` | HTTP Basic доступ к API Mailpit | то же |
| `MEDUSA_ADMIN_EMAIL`, `MEDUSA_ADMIN_PASSWORD` | доступ к admin-API (отмена заказов, уборка) | `admin_client` скипается, сценарии без отмены не идут |
| `MEDUSA_PUBLISHABLE_API_KEY` | публичный ключ витринного API стэнда | часть api-проверок скипается |
| `TCMS_URL`, `TCMS_USER`, `TCMS_PASSWORD` | Kiwi TCMS | перенос результатов в TCMS не выполняется |
| `WEB_URL`, `API_URL`, `REPORTS_URL`, `QA_ENV`, `QA_IS_PRODUCTION` | адреса и режим окружения | берутся значения по умолчанию из `qa/config.py` |
| `QA_EMAIL_DOMAIN` | домен тестовых почт | по умолчанию `example.com` |
| `QA_HOST_OVERRIDES` | подмена адреса стенда в обход локального DNS (см. ниже) | подмены нет, используется системный резолвер |

**В CI адреса — это переменные репозитория (`vars`), а не секреты.** В workflow они
приходят как `WEB_URL: ${{ vars.WEB_URL }}` и `API_URL: ${{ vars.API_URL }}`; в
репозитории заданы `WEB_URL=https://test.tamir.rs` и `API_URL=https://test-api.tamir.rs`
(их можно смотреть и менять в Settings → Secrets and variables → Actions → Variables).
Важная ловушка: если переменная не задана, Actions подставляет **пустую строку**, а не
отсутствующую переменную, — тесты ушли бы на пустой адрес. `qa/config.py` трактует
пустое значение как «переменной нет» и берёт staging-дефолт; в первом браузерном
прогоне именно так и было, и проверка на это есть в `tests/unit/test_config_guard.py`.

**`QA_HOST_OVERRIDES` — только для локального прогона.** Если на рабочей машине
не работает системный DNS, а стенд при этом доступен по IP, переменная закрепляет
адреса вручную: `test.tamir.rs=172.67.143.121,test-api.tamir.rs=172.67.143.121`.
Из одного списка `qa/net.py` делает и подмену `socket.getaddrinfo` для Python-клиентов,
и флаг `--host-resolver-rules` для Chromium, чтобы браузер и API-клиенты видели один и
тот же адрес. В CI переменная не задаётся: runner резолвит сам, а подмена адресов в
прогоне была бы самообманом.

## Про Mailpit

Mailpit — почтовый перехватчик стэнда: вся почта, которую отправляет витрина и
Medusa (коды регистрации, письма о заказах), попадает в него, а не реальным
получателям. Веб-интерфейс и API — `http://192.168.1.143:8025`, доступен **только
внутри локальной сети staging-хоста**, поэтому обращения к нему возможны
исключительно из шагов, которые выполняются на self-hosted runner (`qa-smoke`,
`qa-e2e`). В GitHub-hosted джобе (`qa-unit`, `qa-report`) такие запросы физически не
пройдут, и мы их там не делаем.

Клиент — `qa/mailbox.py`. Доступ к HTTP API защищён Basic auth (отсюда
`MAILPIT_USER`/`MAILPIT_PASSWORD`), эндпоинты:

| Эндпоинт | Что даёт |
| --- | --- |
| `GET /api/v1/messages?limit=N` | список писем (тема, получатель, id) |
| `GET /api/v1/message/{ID}` | тело письма: поля `Text` и `HTML` |

Если Mailpit недоступен или переменные не заданы, фикстура `mailbox` скипает тест с
явной причиной — проверка письма не проходит молча.

## Про прод

Прод-хосты не входят в белый список `qa/config.py::ALLOWED_HOSTS`. Это не
«просьба не трогать проду», а проверка в коде: конструирование клиента на
`https://tamir.rs` и любой запрос на прод-хост падают с `RuntimeError`.
Дополнительно `is_allowed_target` вызывается при загрузке конфигурации, поэтому
ошибка про прод появляется до первого запроса, а не в середине сценария.
