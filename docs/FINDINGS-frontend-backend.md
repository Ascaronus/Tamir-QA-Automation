# Находки на стыке фронтенда и бэкенда (staging, Tamir Balkan)

Документ — отчёт QA для разработки: что ведёт себя не так, как ожидает тест, и что с этим
делают тесты. Он не заменяет план тестирования ([TEST-PLAN.md](TEST-PLAN.md)) и не является
баг-трекером: здесь только то, что **подтверждено запросами и браузером на стенде**.

Стенд: витрина Next.js `https://test.tamir.rs`, Medusa `2.13.6` на
`https://test-api.tamir.rs`, регион `reg_01KN9XP52DQZ1FWKRZ4PMVVR`, валюта `rsd`.
Дата наблюдений: 23–24.11.2026. Все идентификаторы (`cart_…`, `order_…`, `so_…`) — из
тестовых прогонов на стенде; их наличие в списке заказов стенда — норма, они отменяются.

Как получены факты: разовые HTTP-пробы и проходы в Playwright (headless chromium).
Скрипты проб в репозиторий не попали — в репозитории остаются только проверки, которые
эти факты закрепляют (`tests/`, `qa/`). Ни ключей, ни токенов, ни паролей здесь нет:
учётные данные тестовых пользователей читаются из переменных окружения
(перечень — [ENVIRONMENTS.md](ENVIRONMENTS.md)).

## 1. Как читать

| Код | Что это | Где закреплено |
| --- | --- | --- |
| `F-ENV-*` | стенд и его защита | TEST-PLAN §13.1 |
| `F-SEO-*`, `F-CAT-*` | индексация и каталог | TEST-PLAN §13.1 |
| `F-LOC-1` | маршрутизация локалей (почему снята с проверок) | TEST-PLAN §13.2 |
| `F-UI-*` | поведение витрины в браузере | TEST-PLAN §14 |
| `F-API-*` | контракт витринного и админского API | TEST-PLAN §15 |
| `F-REG-*` | регистрация и вход покупателя | тест готовится |
| `F-DATA-1` | данные стенда (имена опций доставки) | не закреплено, ждём ответа |

Статус у записи один из трёх:

* **открыто** — просим поправить или подтвердить, что так задумано;
* **принято как данность** — тест подстроился, правок не просим;
* **ждём ответа** — неясно, баг это или feature.

Приоритет — не серьёзность бага, а цена для автотестов: *высокий* = тесты придётся
переписывать при каждом изменении, *низкий* = неудобство.

## 3. Локали и адреса: почему этот контур снят с проверок

**F-LOC-1 (открыто, высокий).** Адреса страниц «плывут»: одна и та же страница отдаётся
то под англоязычным путём, то под сербским, а часть путей не отдаёт ничего. Ответы стенда
из зонда 24.11.2026:

| Запрос | Ответ |
| --- | --- |
| `/rs/catalog` | 200, страница каталога |
| `/rs/katalog` | 404 |
| `/rs/products` | 404, списка товаров нет |
| `/rs/products/<slug>` | 200, карточка товара работает |
| `/rs/cart/` | 308 на `/rs/cart`, итоговая страница — `/rs/korpa` |
| `/en/cart` | 200 |
| `/me` | 308 на `/rs` |
| `/rs/` и `/en/` | 308 на адрес без слэша |

Содержимое при этом правильное — падает только проверка, завязанная на адрес. Ранняя
версия SEO-контура ждала `/rs/cart` → `/rs/korpa` и держала сербские пути каноническими;
на текущей сборке часть путей англоязычные, часть сербские, а `/rs/products` вообще 404.
Поэтому проверки адресов, `canonical` и `hreflang` из контура убраны (TEST-PLAN §13.2),
а функциональные проверки идут по кликам по ссылкам витрины, а не по заранее известным URL.

Отдельно: `canonical` на страницах стенда указывает на публичный домен
(`https://tamir.rs/rs/products/...`), а не на хост стенда — для поискового индекса это
безопасно ровно пока стоит `noindex` (F-SEO-2).

**Просим:** зафиксировать одно правило — какие адреса канонические (`/rs/katalog` или
`/rs/catalog`, `/rs/korpa` или `/rs/cart`), какие редиректы между локалями обязательны и
что должен отдавать `/rs/products`. После этого проверки адресов вернутся в план.

## 5. Контракт API (M3)

### 5.1 Поля ответа: `fields=` работает выборочно

**F-API-2 (открыто, высокий).** `GET /store/carts/{id}` без `fields=` отдаёт 44 поля,
включая все итоги. С полным `fields=` — 13 ключей. При этом часть запрошенных полей
**молча игнорируется**: ответ 200, но ключей нет.

| Запрошено в `fields=` | В ответе |
| --- | --- |
| `items.title`, `items.unit_price`, `items.variant_id`, `items.variant_title`, `items.product_id`, `items.product_handle`, `items.product_title` | приходят |
| `items.quantity`, `items.raw_quantity`, `items.subtotal`, `items.total` | **не приходят** (и в store-, и в admin-запросах) |

Проверено на заказе `order_01M8582MF7KCPR08SB1QXKYNDS` и на корзине из того же прогона.
Тот же эффект на админском чтении: запрос `id,items.id,items.quantity` возвращает позицию
без `quantity`.

Связано с этим: у позиции **корзины** полей `total`/`subtotal` нет вовсе (есть
`unit_price` и `quantity`) — сумма позиции считается как `unit_price * quantity`.
И наоборот, `fields=` у `GET /admin/orders` возвращает больше, чем просили:
`status`, `version`, `fulfillments`, `payment_collections` приходят всегда.

**Что делают тесты:** количество позиций читают заказом **без** `fields=`, итоги —
отдельным `GET`; составы полей зафиксированы в `qa/medusa_store.py::CART_FIELDS`
и `ORDER_FIELDS`, и это не «оптимизация», а носитель факта.
**Просим:** либо отдавать `items.quantity` в проекции, либо задокументировать список
полей, которые `fields=` не отдаёт.

**F-API-3 (открыто, высокий).** Любое `fields=` запроса корзины, содержащее
`payment_collections.*` (`payment_collections.id`, `payment_collections.sessions`),
отвечает **HTTP 500** `unknown_error`, а не 400. Тот же состав без этих полей — 200.
Это единственный способ получить 500 из витринного API без сломанных данных.
**Что делают тесты:** о платежных коллекциях в запросах корзины молчат, id сессий читают
из ответов mutation-эндпоинтов. **Просим:** 400 с внятным `message` вместо 500.

### 5.2 Мутации и состояние

**F-API-4 (принято как данность, средний).** Ответы мутаций разнородны и почти всегда
частичные:

| Шаг | Ответ |
| --- | --- |
| `POST /store/carts` | `{"cart": {...}}` |
| `POST /store/carts/{id}/line-items` | `{"cart": {...}}` с итогами |
| `POST /store/carts/{id}/line-items/{line_id}` (смена количества) | без привычных итогов |
| `DELETE /store/carts/{id}/line-items/{line_id}` | `{"id":…, "object":"line-item", "deleted":true, "parent":{…}}` — ключа `cart` нет, корзина в `parent` |
| `POST /store/carts/{id}/shipping-methods`, `/shipping-address` | корзина без сумм |
| `POST /store/carts/{id}/complete` | `{"type":"order","order":{…}}`, ключа `metadata` в ответе нет |

**Что делают тесты:** успешный ответ любой мутации перечитывается `GET /store/carts/{id}`
(`qa/medusa_store.py::_after_mutation`), поэтому проверки видят то же, что видит
покупатель на странице корзины, а отказ остаётся данными, которые вернул API.

Чего на этой сборке **нет** (всё — 404 `Cannot GET/PUT/DELETE …`):
`GET /store/carts`, `DELETE /store/carts/{id}`, `PUT /store/carts/{id}/line-items/{id}`
(количество меняют **POST**-ом), `POST /store/orders/{id}/confirmation`.
Отдельно: `GET /store/orders/{id}?email=…` отвечает 400
`Unrecognized fields: 'email'` — параметр трактуется как селектор полей.

**F-API-7 (открыто, высокий).** Корзину нельзя удалить целиком: `DELETE /store/carts/{id}`
→ 404, `GET /admin/carts` → 404 (в админке списка корзин нет). Корзина удаляется только
снятием позиций: `DELETE /store/carts/{id}/line-items/{line_id}` → 200 и бронь товара
освобождается. Из-за этого уборка в тестах идёт по позициям (`remove_all_items`), а
незавершённые корзины дожидаются срока жизни и держат резерв на складе стенда.
**Просим:** маршрут удаления корзины (или срок жизни покороче и наружу).

**F-API-8 (открыто, средний).** Админский список заказов не фильтруется по
`?metadata.qa_run=` и `?display_id=` — параметры игнорируются, приходит вся выборка.
Поиск тестовых заказов идёт постранично на стороне клиента
(`qa/medusa_admin.py::find_qa_orders`). На сотнях заказов это станет медленным.
**Просим:** фильтр по `metadata` (или по `display_id`) на `/admin/orders`.

**F-API-6 (принято как данность, низкий).** Отменённый заказ отвечает всеми итогами `0`
и в витринном, и в админском представлении (`total`, `subtotal`, `item_total`,
`shipping_total`, `tax_total`), при этом `items[].unit_price` сохраняется. Повторная
отмена — ошибка, поэтому уборка читает статус до отмены (`POST /admin/orders/{id}/cancel`).

**F-API-5 (принято как данность, низкий).** `POST /store/carts/{id}/complete` в ответе
не имеет ключа `metadata`, но `metadata.qa_run`, записанный в корзину, приходит и в
витринном заказе, и в `GET /admin/orders/{id}`. Именно по этой метке уборка находит и
отменяет тестовые заказы (TEST-PLAN §16).

### 5.3 Данные стенда, на которые опираются проверки

| Что | Значение |
| --- | --- |
| Каталог | 16 товаров, цены `1290`–`1750` RSD (`calculated_price.amount`, минорные единицы) |
| Остатки | поле `stock` = 1…10, `inventory_quantity` = `null`, `allow_backorder` = `false` |
| Товары с `stock >= 2` | `demisezonski-sesir-plave-boje` (2), `muska-zimska-kapa-u-sivoj-boji` (5), `muska-zimska-kapa-u-plavoj-boji` (10) |
| Доставка | `so_01M2T3C1BRF93DMP9M2JW3FC1S` «Store Pickup» 0 RSD; `so_01M2T3HWWFBA5AQ38R6XK7JJH3` — `" Shipping"` с ведущим пробелом (F-DATA-1) |
| Оплата | `pp_system_default` (Cash on Delivery) проходит без внешних платёжных ключей |

`inventory_quantity = null` при непустом `stock` — **ждём ответа**: это либо остаток не
считается, либо поле не отдаётся по конфигурации. Тесты читают `null` как «нет данных», а
не как «нулевой остаток» (`qa/medusa_store.py::variant_stock`), и не проверяют «склад
кончился» по этому полю.

**F-DATA-1 (открыто, низкий).** У второй опции доставки имя — `" Shipping"` с ведущим
пробелом. В витрине это не видно, но любое сравнение имён опций в тестах и в отчётах
на этом спотыкается. **Просим:** поправить данные.

## 6. Регистрация, вход и почта

Это тот участок, где пользовательский сценарий упирается в защиту и в почту.
E2E-проверка регистрации (`tests/e2e/test_registered_customer_journey.py`) готовится,
поэтому здесь — описание контракта, полученного вручную, без ссылок на код проверок.

| Код | Наблюдение | Приоритет | Статус |
| --- | --- | --- | --- |
| F-REG-1 | Регистрация защищена Cloudflare Turnstile: на форме есть скрытое поле `cf-turnstile-response`, скрипт `challenges.cloudflare.com/turnstile/v0/api.js`; без токена заявка не проходит | высокий | принято |
| F-REG-2 | Заявка регистрации уходит на `POST /store/registration/start` витринного API. Без токена Turnstile запрос не отправляется вообще: в логе сети только скрипты `challenges.cloudflare.com`, а ожидание ответа на `registration/start` не наступает | средний | принято |
| F-REG-3 | Код подтверждения приходит письмом в Mailpit, тема `TAMIR - Kod za registraciju / Registration code` (обычный дефис, без диакритики); код — шесть цифр в тексте письма | средний | принято |
| F-REG-4 | Покупателя, созданного админкой (`POST /admin/customers`), **нельзя** использовать как тестовый аккаунт: у него `has_account: false`, `POST /auth/customer/emailpass` → 401 `Invalid email or password`, а `POST /auth/customer` → 404 | высокий | открыто |
| F-REG-5 | В `metadata` покупателя витрина хранит служебные поля: `registration_challenge` (хеш), `consent_version`, `terms_accepted_at`, `privacy_acknowledged_at`, `email_verified_at`, `tamir_welcome_sent_at`; у части старых записей `metadata` вообще `null` | низкий | принято |
| F-API-9 | Подтверждение заказа приходит письмом `TAMIR — Porudžbina / Order #<display_id>` от `staging@tamir.local` — с диакритикой и длинным тире. В `frontend/messages` и в поиске тестов тема без диакритики («Porudzbina»), у письма о регистрации наоборот дефис | низкий | принято |

**F-REG-4 — главная просьба в этом разделе.** Тест не может «подготовить покупателя
админкой» и войти под ним, поэтому покупателю приходится проходить регистрацию в UI:
это самый хрупкий шаг сценария (Turnstile, письмо, ожидание кода). Варианты, которые
устроили бы тесты: предзаведённый тестовый аккаунт с паролем, сервисный маршрут для
выпуска тестовой сессии, или отключение Turnstile для тестового адреса на стенде.

Как тесты обходят остальное:

* Turnstile и отправка кода — только через UI, с ожиданием ответа, а не прямым вызовом API;
* письмо читается из Mailpit API (`qa/mailbox.py`): сообщения ищутся по адресату, код
  выбирается шестью цифрами в тексте, а письмо заказа — подстрокой `porud|order` в теме,
  чтобы расхождение диакритики и тире не ломало проверку;
* `metadata.qa_run` в корзине и заказе — признак «это тестовые данные», по нему уборка
  отменяет заказы и удаляет покупателей (`scripts/qa_cleanup.py`, TEST-PLAN §16).

## 7. Что просим сделать (сводка)

1. Добавить `data-testid` на четыре элемента пути покупателя (F-UI-1).

   правило, что UI может быть без неё (F-UI-2).

4. Отдавать `items.quantity`/`items.raw_quantity` в проекции `fields=` или задокументировать
   исключения (F-API-2).
5. Заменить 500 на 400 для недопустимых полей в `fields=` (F-API-3).
6. Дать маршрут удаления корзины или список корзин в админке (F-API-7).
7. Добавить фильтр `/admin/orders?metadata.…` (F-API-8).
8. Исправить имя опции доставки `" Shipping"` с ведущим пробелом (F-DATA-1).
9. Дать способ получить тестового покупателя без Turnstile (F-REG-4).
10. Ответить про `inventory_quantity = null` при непустом `stock` (раздел 5.3).

## 8. Как это соотносится с прогонами

Находки не блокируют CI: тесты обходят их сейчас, а не ждут правок. Что закрыто и что пока
нет — в [REPORTING.md](REPORTING.md) и [TCMS.md](TCMS.md); правила тестовых данных и уборки —
TEST-PLAN §16 и [ENVIRONMENTS.md](ENVIRONMENTS.md).

Обновлять документ нужно в одном случае: когда команда разработки отвечает на пункт из раздела 7
или когда проверка из `tests/` перестаёт подтверждать факт. Тогда меняется строка таблицы и
её статус, а ссылка в TEST-PLAN остаётся прежней.
